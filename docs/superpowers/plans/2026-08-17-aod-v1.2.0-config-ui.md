# Lunaa Adaptive AOD v1.2.0 Configuration UI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a native settings app with an overall brightness slider, editable lux curve, hints/live preview, and make AOD entry immediately reapply a prepared adaptive target instead of visibly sitting at stock `0.05`.

**Architecture:** Preserve the proven v1.1.0 `transitionTo()` runtime-field hook. Configuration is an immutable pure-Java snapshot shared by the app and engine; the app writes `aod_settings`, SystemUI reads it through legacy `XSharedPreferences`, and settings are reloaded at AOD transitions. A pure Doze-state policy prepares an adaptive target before physical DOZE so the existing reset hook can immediately overwrite stock `0.05` during the transition window.

**Tech Stack:** Java 17, Android 16 / compileSdk 36, platform Android widgets only, legacy Xposed API compile-only stubs, `XSharedPreferences`, JUnit-style JVM tests, PowerShell Windows builder.

## Global Constraints

- Target remains crDroid 12.11 / Android 16 / `lunaa`.
- Xposed scope remains only `com.android.systemui`.
- Keep v1.1.0 runtime attachment through `transitionTo()` and exact runtime fields `mSensorManager`, `mDisplayManager`, `mHandler`.
- Do not restore `DozeScreenBrightness.mContext`, constructor hooks, or `ActivityThread.currentApplication()`.
- Do not hook System Framework / `android`.
- Do not hook UDFPS in v1.2.0.
- Fail open on missing/invalid cross-process settings.
- Settings take effect on the next AOD activation; no polling loop.
- Use platform widgets only; no AndroidX/Material dependency.
- Release version is `1.2.0`, `versionCode = 6`.
