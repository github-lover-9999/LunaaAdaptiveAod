# Lunaa Adaptive AOD v1.1.0 — Runtime Attachment Design

## Goal

Make controller attachment reliable on the exact July 5, 2026 crDroid 12.11 `lunaa` SystemUI build without relying on source-level members that are absent from the compiled DEX.

This revision changes only controller attachment and dependency acquisition. Brightness curve, hysteresis, fallback floor, light-sensor policy, and SystemUI-only scope remain unchanged.

## Evidence from the exact ROM dump

The installed SystemUI runtime proves `DozeScreenBrightness.transitionTo(...)` is hookable: Vector logs `LunaaAOD: transitionTo observed`.

The compiled `DozeScreenBrightness` DEX does not expose `mContext`, so the v1.0.x late-attach path cannot construct `AdaptiveAodController` from a recovered `Context`.

The compiled class does expose the dependencies needed by the controller directly, including `mSensorManager`, `mDisplayManager`, `mHandler`, and `mDozeService`. The existing bridge already uses `mDozeService` reflectively.

The constructor-hook path is not a reliable lifecycle point on this build and is not required once attachment happens from a live `transitionTo()` callback.

## Architecture

### Single attachment path

`SystemUiHooks` hooks `DozeScreenBrightness.transitionTo(oldState, newState)`.

On the first invocation for a `DozeScreenBrightness` instance, `ensureController(instance)` reads these fields directly from that instance:

- `mSensorManager` as `SensorManager`
- `mDisplayManager` as `DisplayManager`
- `mHandler` as `Handler`

It then creates one `AdaptiveAodController` for that exact instance and stores it in the existing identity map.

There is no constructor attachment path and no Context recovery path.

### Explicitly removed mechanisms

v1.1.0 must not contain:

- `XposedBridge.hookAllConstructors(...)`
- reads of `mContext`
- constructor-argument scanning for `Context`
- `ActivityThread.currentApplication()`
- any System Framework / `android` process scope

These are removed rather than retained as fallbacks.

### Controller constructor

`AdaptiveAodController` no longer accepts `Context`.

It receives the exact SystemUI dependencies resolved from `DozeScreenBrightness`:

```text
AdaptiveAodController(
    Object dozeScreenBrightness,
    SensorManager sensorManager,
    DisplayManager displayManager,
    Handler handler
)
```

The supplied SystemUI handler is reused rather than constructing a new main-thread Handler.

### Reset behavior

`resetBrightnessToDefault()` remains hooked only to reapply the already-created controller's adaptive target after the ROM writes its stock doze value.

It is not a second controller-creation architecture. If no controller exists, the reset callback leaves stock behavior untouched and emits at most a bounded diagnostic.

### Lifecycle

- First `transitionTo`: resolve dependencies, attach controller, capture pre-doze brightness.
- Subsequent `transitionTo`: reuse the existing controller.
- After transitions: refresh physical display state as before.
- `resetBrightnessToDefault`: reapply adaptive value only if controller already exists.
- `FINISH`: destroy controller and remove it from the identity map.

## Failure handling

Dependency acquisition is all-or-nothing for controller creation.

If a required field is missing, null, or of the wrong runtime type:

1. do not create a partial controller;
2. do not throw into SystemUI;
3. leave stock AOD behavior active;
4. write a Vector-visible diagnostic naming the failed dependency;
5. avoid unbounded repeated logging.

No alternate Context or process fallback is attempted.

## Logging / runtime proof

The minimum Vector-visible lifecycle evidence for v1.1.0 is:

```text
LunaaAOD: hooks installed
LunaaAOD: transitionTo observed
LunaaAOD: controller attached source=runtime-fields
```

If attachment fails, the log must identify the exact field/type, for example:

```text
LunaaAOD: controller attach failed: mHandler unavailable
```

Normal logcat continues to carry light-sensor registration, lux, display-state, and applied-target diagnostics.

## Scope intentionally unchanged

v1.1.0 does not change:

- brightness curve or maximum/floor values;
- hysteresis/debounce behavior;
- pre-sleep lux capture;
- normal-screen brightness fallback sampling;
- `DozeBridge` brightness application semantics;
- UDFPS implementation;
- ROM overlays;
- system_server / framework hooks;
- module scope (`com.android.systemui` only).

UDFPS becomes a separate investigation only if adaptive doze brightness is proven to attach and apply but is later overwritten during UDFPS hide.

## Verification requirements

Before release, tests must prove:

1. `SystemUiHooks` contains no constructor hook or Context fallback.
2. `transitionTo()` is the only controller-creation path.
3. dependency extraction validates `mSensorManager`, `mDisplayManager`, and `mHandler` types.
4. `resetBrightnessToDefault()` never creates a controller.
5. controller identity is one-per-`DozeScreenBrightness` instance.
6. `FINISH` destroys and removes the controller.
7. Xposed stub ABI checks still pass.
8. existing brightness/policy tests still pass unchanged.
9. Android build completes and produces a clean standalone v1.1.0 APK/source package.

## Runtime acceptance test

After installing v1.1.0, enabling only System UI scope, and performing a full reboot, a real screen-off/AOD cycle must first produce:

```text
LunaaAOD: transitionTo observed
LunaaAOD: controller attached source=runtime-fields
```

Only after this is proven do we evaluate sensor registration and whether `dumpsys display` moves away from the ROM's fixed `0.05` target according to ambient light.
