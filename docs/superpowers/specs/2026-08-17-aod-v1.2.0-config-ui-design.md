# Lunaa Adaptive AOD v1.2.0 Configuration UI Design

## Goal

Turn the proven v1.1.0 adaptive AOD engine into a user-tunable module without changing its verified SystemUI attachment architecture. Add an app UI where the user can increase/decrease overall AOD brightness with one slider, edit every lux→brightness point, see human-readable guidance, preview the result from the phone's live light sensor, and reset to safe presets. Also remove the visible `bright screen → stock 0.05 dip → adaptive target` sequence when entering AOD.

## Fixed Constraints

- Target remains crDroid 12.11 / Android 16 / `lunaa`.
- Xposed scope remains **only** `com.android.systemui`.
- Keep v1.1.0 runtime attachment: `transitionTo()` + `mSensorManager` + `mDisplayManager` + `mHandler`.
- Do not restore `DozeScreenBrightness.mContext`, constructor hooks, or `ActivityThread.currentApplication()`.
- Do not hook System Framework / `android`.
- Do not hook UDFPS in v1.2.0.
- Fail open: unreadable/invalid settings use built-in defaults; stock SystemUI must remain usable.
- Release version is `1.2.0`.

## Approaches Considered

### A. Legacy `XSharedPreferences` + native Android settings Activity — selected

The app writes a dedicated `aod_settings` SharedPreferences file. The hooked SystemUI process reads it through legacy `XSharedPreferences` and reloads it at AOD transitions. The manifest declares the LSPosed/Vector shared-preferences extension metadata. This preserves the already-proven legacy hook stack and requires no Context dependency inside SystemUI.

### B. Migrate configuration transport to modern libxposed Remote Preferences — rejected for this release

Remote Preferences offer change listeners and a cleaner modern transport, but moving the working module from legacy hooks to modern libxposed at the same time as adding settings would mix two large changes and increase regression risk.

### C. Exported ContentProvider read from SystemUI — rejected

This would require obtaining a SystemUI `Context` and add another reflective/runtime dependency solely for configuration transport. It conflicts with the v1.1.0 simplification goal.

## Settings Model

`AodSettingsSnapshot` is immutable and contains:

- `enabled` — master adaptive-AOD switch, default `true`.
- `multiplierPercent` — global curve multiplier, integer `50..300`, default `100`.
- 9 ordered curve points `(lux, brightness)`.
- `revision` — monotonically increasing integer used only for diagnostics.

Built-in **Balanced** curve becomes brighter than v1.1.0 while keeping dark-room values restrained:

| Point | Lux | Brightness | Hint |
|---|---:|---:|---|
| 1 | 0 | 0.020 | almost complete darkness |
| 2 | 2 | 0.025 | very dark room |
| 3 | 10 | 0.045 | dim room |
| 4 | 50 | 0.090 | evening / low indoor light |
| 5 | 200 | 0.160 | typical indoor light |
| 6 | 500 | 0.230 | bright indoor light |
| 7 | 1000 | 0.300 | bright window / shaded daylight |
| 8 | 5000 | 0.450 | strong daylight |
| 9 | 20000 | 0.600 | very bright daylight |

Additional presets:

- **Dim:** conservative curve close to v1.1.0.
- **Balanced:** default curve above.
- **Bright:** stronger daytime values, capped below 1.0 before multiplier.

Runtime output is:

`clamp(interpolate(curve, lux) × multiplierPercent / 100, 0.010, 1.000)`.

The multiplier is deliberately global: it preserves the shape of a custom curve and gives the user one obvious day-to-day control.

## Validation

On save:

- exactly 9 points are required;
- every lux value must be finite, `>= 0`, and strictly greater than the previous point;
- brightness must be finite and within `0.010..1.000`;
- multiplier must be within `50..300`;
- invalid rows are not persisted and the UI shows a precise row-level error;
- values above `0.50` show a warning that high AOD brightness increases power use and OLED wear, but remain allowed up to `1.0`.

If SystemUI reads malformed/missing preferences, the settings reader returns the full built-in Balanced snapshot rather than partially applying broken data.

## App UI

One launcher Activity using platform Android widgets only; no AndroidX/Material dependency.

Top section:

- title `Lunaa Adaptive AOD`;
- master switch `Adaptive AOD`;
- status text: `Changes apply on the next AOD activation`;
- live sensor readout: `Ambient light: 64 lux`;
- preview: `Calculated AOD brightness: 0.184`.

Main control:

- `Overall brightness` SeekBar, `50%..300%`, 5% steps;
- numeric value next to it;
- explanation: `Scales the whole curve without changing its shape.`

Presets:

- `Dim`, `Balanced`, `Bright` buttons;
- applying a preset updates the editable rows but does not immediately save until `Save`.

Advanced curve:

- 9 rows;
- each row has editable Lux and Brightness fields;
- each row includes a short human-readable lighting hint;
- brightness is shown as a normalized panel request (`0.000–1.000`) with text explaining that it is not perceived linear screen percentage.

Actions:

- `Save` validates and persists;
- `Reset` restores Balanced values and multiplier 100%;
- save confirmation includes the revision and reminder to cycle AOD.

The Activity registers its own `TYPE_LIGHT` listener while visible so preview updates live without depending on the hooked SystemUI process.

## Cross-process Configuration Transport

App process:

1. open `aod_settings` with `Context.MODE_WORLD_READABLE` when supported by the Xposed shared-preferences extension;
2. persist all values atomically with `SharedPreferences.Editor.commit()`;
3. increment `revision` only after validation;
4. if framework support is unavailable and `MODE_WORLD_READABLE` throws, show a visible error and do not claim the settings are active.

SystemUI process:

1. `XposedSettingsReader` owns `XSharedPreferences("dev.lunaa.aod", "aod_settings")`;
2. call `reload()` before each AOD-target transition and before creating/reusing the controller for a new ambient cycle;
3. parse a complete `AodSettingsSnapshot`;
4. engine receives the new snapshot before calculating the entry target;
5. log `settings revision=<n> multiplier=<n>%` once when revision changes.

No listener/polling loop is required. Saving while AOD is already active takes effect on the next screen-on → AOD cycle.

## Startup Dip Fix

The current dip exists because stock `resetBrightnessToDefault()` can write `0.05` before the physical display state has changed to DOZE, while v1.1.0 only applies the adaptive entry target after the display listener reports an ambient state.

v1.2.0 adds a pure `DozeStatePolicy` based on the actual `DozeMachine.State` names present in the user's SystemUI (`DOZE`, `DOZE_AOD`, `DOZE_AOD_DOCKED`, `DOZE_AOD_MINMODE`, `DOZE_AOD_PAUSING`, `DOZE_AOD_PAUSED`).

Flow:

1. `transitionTo(oldState, newState)` before-hook marks whether the transition intends an ambient/AOD state and refreshes settings.
2. Before stock reset can become visually persistent, the controller computes a pending target from the most recent valid lux. If recent lux is unavailable, it uses the pre-doze screen-brightness seed.
3. `resetBrightnessToDefault()` after-hook calls `reapplyAfterReset(pendingAmbientIntent)`.
4. If physical display state is not DOZE yet but `pendingAmbientIntent` is true, reapply the pending adaptive target instead of leaving stock `0.05` visible.
5. Once the display becomes DOZE/DOZE_SUSPEND, normal ALS adaptation continues exactly as before.
6. Transitions to `FINISH` clear the pending intent and destroy the controller as in v1.1.0.

This is not a UDFPS hook and does not alter stock state-machine decisions; it only prevents the known `0.05` reset from winning during the short transition window.

## Component Boundaries

- `AodSettingsSnapshot`: immutable validated runtime values.
- `AodSettingsDefaults`: built-in Dim/Balanced/Bright curves and hints.
- `AodSettingsCodec`: shared preference keys and parsing/serialization rules.
- `XposedSettingsReader`: read-only SystemUI-side adapter using XSharedPreferences.
- `SettingsActivity`: app UI and app-side persistence/live preview.
- `BrightnessCurve`: generic interpolation using a supplied snapshot instead of static arrays.
- `AdaptiveAodEngine`: current sensor/history/gating state plus replaceable settings snapshot.
- `DozeStatePolicy`: pure classification of state names for pending ambient intent.
- `AdaptiveAodController`: applies settings, manages ALS/display listeners, and exposes pending-intent reapply.
- `SystemUiHooks`: passes transition intent and triggers settings reload; still the only hook wiring layer.

## Testing

Pure JVM tests cover:

- interpolation with custom curve;
- multiplier clamp and output cap;
- invalid snapshot rejection/fallback;
- preset values/order;
- settings revision reload behavior through a fake key-value source;
- `DozeStatePolicy` state classification;
- entry target available before physical DOZE when ambient intent is set;
- reset reapply path never creates a controller;
- existing v1.1.0 runtime-field wiring remains present and forbidden Context/constructor paths remain absent;
- release metadata and SystemUI-only scope.

Android compile verification additionally checks Activity/SharedPreferences/Sensor APIs and the exact legacy `XSharedPreferences` descriptors used by production code.

## Acceptance Criteria

1. Existing v1.1.0 runtime attachment still logs `controller attached source=runtime-fields` on device.
2. App opens from launcher and saves a multiplier/curve without root UI interaction.
3. Next AOD cycle logs the new settings revision and uses the saved curve.
4. At stable lighting, changing multiplier from 100% to 200% approximately doubles the requested AOD brightness until capped.
5. Covering/uncovering the light sensor still changes brightness live during DOZE.
6. On entry to AOD, there is no visible/stable fallback interval at stock `0.05`; the pending adaptive target is reapplied immediately after stock reset.
7. UDFPS disappearance does not reset the adaptive target.
