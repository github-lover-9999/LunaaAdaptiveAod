# Lunaa Adaptive AOD v1.5.3 — root bridge hardening audit

## Evidence that changed the design

On crDroid 12.11 / Android 16, the injected `com.android.systemui` process is observed with runtime UID `10301`, not UID 1000. v1.5.2 therefore rejected a legitimate ordered broadcast before any root/sysfs write. Manual 100% and the Extra Bright policy had already reached the dim-layer stage, proving that sender validation—not brightness policy—was the immediate failure.

The same trace shows the fingerprint authentication client can remain active after the stock `OnscreenFingerprint mode: Exit`. That coexistence is a device-level QA item after the root bridge is actually accepted; it cannot be declared fixed from static analysis.

## v1.5.3 invariants

- Never execute `su` from injected SystemUI.
- Trust only the framework-reported `com.android.systemui` sender whose runtime UID owns that package and whose package is a system/updated-system app. Do not hard-code UID 1000.
- Declare SystemUI package visibility explicitly.
- Execute root writes only in `dev.lunaa.aod` and only to the hard-coded `notify_fppress` path.
- Preserve the proven `0 -> 1` edge.
- Serialize root commands and generation-gate them so a newer reset/enable supersedes stale work.
- Keep the protective dim layer attached before any possible HBM enable.
- If policy turns off while the edge is in flight, keep the layer until the result is known.
- If an enable result is lost/ambiguous, latch the existing protective layer for the AOD session.
- If reset fails or its result is lost, retain the layer through a bounded stock-display-exit window, then remove it so normal UI cannot remain obscured.
- A failure to update an already-attached dim layer must preserve the existing layer rather than remove protection after HBM may be active.
- Hidden `DisplayManager.mContext` is optional. Failure to resolve it disables only Extra Bright; normal adaptive AOD still attaches from the proven runtime fields.
- Settings read/decode/null failures fail closed to stock behavior.
- `FINISH` and controller destruction explicitly terminate the Extra Bright session.
- Automatic Extra Bright must not use indefinitely stale Lux.

## Device acceptance gate

A release is not considered physically verified until a fresh v1.5.3 device trace contains, in order:

1. `Accepted SystemUI sender uid=... package=com.android.systemui`
2. `HBM edge executed via app root process`
3. `extraBright rootBridge result=true detail=edge-0-to-1`
4. kernel `notify fingerpress on`
5. kernel `qcom,mdss-dsi-aod-hbm-on-command`
6. no unexpected HBM-off transition during the observation window, or a captured cause if one occurs.
